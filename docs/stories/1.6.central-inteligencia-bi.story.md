## Story

**As an** administrador ou gerente logado no SobControle,
**I want** uma "Central de Inteligência" dentro de Relatórios que mostre, em formato de vitrine, todos os módulos analíticos (atuais e futuros) do Gestly BI — com seus benefícios, indicadores, status de acesso e caminho claro para desbloquear os que ainda não tenho — sem expor dados de módulos que minha empresa não contratou,
**so that** eu entenda o valor de cada recurso analítico disponível, acesse imediatamente os que já tenho direito, e saiba exatamente o que preciso fazer (falar com o time / upgrade de plano) para desbloquear os demais.

## Scope Decisions (confirmadas com o usuário antes da implementação)

1. **Destino do "Acessar análise":** os 4 módulos "Analytics de X" (Vendas/Clientes/Financeiro/Estoque) descrevem indicadores que ainda não existem no produto (funil por etapa, churn score, fluxo de caixa projetado, giro de estoque, desempenho de fornecedores, etc.). Construir todos esses indicadores é um épico à parte. Nesta story, "Acessar análise" navega para a superfície existente mais próxima: Dashboard Executivo → `/dashboard`; Analytics de Vendas/Clientes/Financeiro/Estoque → a aba correspondente já existente em `/reports` (`sales`/`customers`/`financial`/`inventory`); Gestly Insights → a Central de Notificações já existente (`/notifications`), que já entrega literalmente "central de alertas e recomendações inteligentes" (Story 1.5). Nenhuma tela nova de análise profunda é construída nesta story — fica documentado como próxima story/épico.
2. **Ação de desbloqueio:** os botões "Conhecer plano"/"Desbloquear módulo" em módulos bloqueados **nunca** concedem acesso real — apenas abrem um modal com os benefícios do módulo e um link para Configurações → Assinatura (`/settings`, aba já existente). Não há pagamento real nem ativação self-service nesta story (conforme instrução explícita do usuário). As tabelas `company_analytics_modules`/histórico ficam com o schema pronto para uma futura integração de billing/back-office popular, mas nenhuma escrita é feita a partir desta UI.
3. **Testes automatizados:** o projeto não possuía nenhum framework de testes configurado (mesma lacuna documentada nas Stories 1.1–1.5). Como o usuário pediu testes explicitamente desta vez, esta story adiciona Vitest + Testing Library (mínimo necessário) e cobre a lógica de regra de acesso (`resolveModuleAccess`) e a renderização dos 4 estados de card.

## Acceptance Criteria

**Geral / Estrutura:**

1. Nova aba "Central de Inteligência" dentro de `src/pages/reports/ReportsPage.tsx` (mesmo padrão de tabs já existente: Visão Geral, DRE, Vendas, Financeiro, Estoque, Clientes), acessível apenas a quem já acessa `/reports` (`RoleRoute(['admin','manager'])` existente e inalterado — nenhuma rota nova exposta a `employee`).
2. `ReportsPage` passa a ler o parâmetro de URL `?tab=` para definir a aba inicial (deep link), mantendo o comportamento padrão (`overview`) quando ausente/inválido — permite que os cards de módulo já contratado apontem diretamente para a aba certa (ex.: `/reports?tab=sales`).
3. Página da Central de Inteligência exibe título "Central de Inteligência", subtítulo "Transforme dados do seu negócio em decisões mais rápidas.", busca por nome/funcionalidade, filtro por categoria (Todos, Vendas, Clientes, Financeiro, Estoque, Inteligência Artificial) e uma área de destaque "Recomendado pela Gestly" para módulos marcados como recomendados.
4. 6 módulos exibidos nesta story: Dashboard Executivo, Analytics de Vendas, Analytics de Clientes, Analytics Financeiro, Analytics de Estoque e Compras, Gestly Insights — cada um com nome, descrição, 3 benefícios objetivos, lista de indicadores/visualizações que serão liberados, badge de status e CTA adequado ao status.
5. 4 estados de card, cada um com renderização e regra de acesso distintas: **Disponível** (incluído no plano atual, sem necessidade de contratação — CTA "Acessar análise"), **Contratado** (add-on ativo em `company_analytics_modules` para a empresa — CTA "Acessar análise"), **Em breve** (`is_coming_soon = true` no catálogo — sem CTA, badge "Em breve"), **Bloqueado** (não incluído no plano nem contratado — ícone de cadeado, selo "Recurso premium", benefícios resumidos, CTA "Conhecer plano" ou "Desbloquear módulo" conforme `is_addon`).
6. CTA de módulo bloqueado abre `BiUnlockModal` (nunca concede acesso — ver Scope Decision 2) com nome/benefícios do módulo e botão que navega para `/settings?tab=subscription` (aba Assinatura já existente).
7. Estados de loading (skeleton de cards), erro (mensagem + retry) e vazio (busca/filtro sem resultado) implementados, seguindo os padrões visuais já usados em `ReportCard`/`OverviewTab`.
8. Zero comentários desnecessários no código de aplicação; todo texto visível ao usuário em PT-BR; TypeScript estrito; ícones via `lucide-react`; feedback via `sonner` onde aplicável.

**Task 1 — Schema (catálogo, contratação, auditoria):**

9. Nenhuma das 3 tabelas a seguir pré-existia (confirmado via `mcp__supabase__list_tables` antes da implementação): `analytics_modules` (catálogo global, sem `company_id` — referência do sistema, mesmo padrão de `notification_templates` com `company_id IS NULL`), `company_analytics_modules` (add-ons contratados por empresa, `company_id` + `UNIQUE(company_id, module_key)`), `company_analytics_module_history` (log de auditoria de ativação/desativação, somente leitura para o cliente — escrita só via trigger `SECURITY DEFINER`). Todas criadas em `supabase/migrations/20260710090000_analytics_modules_schema.sql`, com RLS habilitado e `REVOKE ALL ... FROM anon`.
10. `analytics_modules`: leitura liberada a qualquer usuário autenticado (dado não sensível, mesmo padrão de templates globais); nenhuma política de escrita para `authenticated` — catálogo é gerenciado via migration/seed, não pelo cliente.
11. `company_analytics_modules`: leitura restrita a `company_id = get_user_company_id()`; escrita (INSERT/UPDATE/DELETE) restrita a `admin`/`manager` da própria empresa (mesmo padrão de `notification_rules`) — pronta para uma futura tela de back-office/billing popular, mas **nenhum caminho do frontend desta story escreve nesta tabela** (ver Scope Decision 2).
12. `company_analytics_module_history`: leitura restrita à própria empresa; populada automaticamente por trigger (`log_analytics_module_change()`, `SECURITY DEFINER`) a cada INSERT/UPDATE de status em `company_analytics_modules` — não existe política de INSERT para `authenticated`, evitando que o cliente forje entradas de auditoria.
13. Seed do catálogo (6 módulos) inserido via `ON CONFLICT (key) DO NOTHING` na própria migration: `dashboard_executivo` (categoria `geral`, `min_plan = NULL` → incluído em qualquer plano ativo), `sales_analytics`/`customer_analytics`/`financial_analytics`/`inventory_analytics`/`gestly_insights` (categorias `vendas`/`clientes`/`financeiro`/`estoque`/`ia`, `min_plan = 'enterprise'`, `is_addon = true`) — como toda empresa nasce no plano `pro` (`complete_company_signup`), os 5 últimos aparecem como "Bloqueado" por padrão para qualquer empresa nova, demonstrando o funil de upsell; uma empresa no plano `enterprise` os vê automaticamente como "Disponível".
14. Migration aplicada ao projeto Supabase remoto via `mcp__supabase__apply_migration` durante esta story. `mcp__supabase__get_advisors(security)` revisado após a aplicação, sem novos avisos `ERROR`.
15. Migration espelhada em `supabase_schema.sql` (tabelas, índices, RLS, trigger, seed), conforme convenção do projeto.

## Dev Notes

### Contexto do projeto

Não há `docs/architecture/` nem PRD sharded neste repositório (mesmo contexto brownfield das Stories 1.1–1.5). Todo o contexto técnico foi extraído do código-fonte existente (`ReportsPage.tsx`, `SettingsPage.tsx`, `notificationService.ts`, `settingsService.ts`, `supabase_schema.sql`) e de introspecção direta do banco via MCP Supabase.

### Por que a aba vive dentro de Relatórios em vez de um item novo na Sidebar

`Sidebar.tsx` usa uma estrutura plana de seções/itens, sem suporte a sub-navegação aninhada. `ReportsPage.tsx` já implementa exatamente o padrão de "subseção dentro de uma aba" pedido (Visão Geral, DRE, Vendas, Financeiro, Estoque, Clientes como tabs). Adicionar "Central de Inteligência" como mais uma tab reaproveita esse padrão em vez de inventar uma nova convenção de navegação aninhada na Sidebar.

### Por que os 5 módulos além do Dashboard Executivo exigem plano `enterprise`

Toda empresa nasce com `subscriptions.plan = 'pro'` (`complete_company_signup`). Se esses módulos exigissem apenas `'pro'`, todas as empresas os veriam como "Disponível" imediatamente, o que contradiz o objetivo de vitrine/upsell do brief (mostrar valor antes de mostrar a restrição). Exigir `'enterprise'` faz com que toda empresa nova experimente o funil completo (bloqueado → benefícios → CTA → tela de planos) enquanto uma empresa já no plano superior os recebe automaticamente.

### `company_analytics_modules` sem caminho de escrita no frontend

Ver Scope Decision 2. A tabela, RLS e trigger de auditoria estão prontos para uma futura tela de contratação/billing, mas nenhum botão desta story insere linhas nela — os testes do estado "Contratado" usam dados mockados na camada de teste, não uma ativação real, exatamente como pedido pelo usuário ("não criar pagamento real nesta etapa").

### Descoberta: `npm run lint` estava quebrado desde a Story 1.3 (não relacionado à Central de Inteligência)

Ao executar `npm run lint` para esta story, o comando falhou por dois motivos, ambos pré-existentes e confirmados via `git log`/`git blame` como anteriores a esta sessão:

1. `package.json` usava a flag `--ext ts,tsx`, incompatível com o `eslint.config.js` (flat config) já commitado desde a Story 1.3.
2. Mesmo corrigida a flag, `eslint.config.js` importava `eslint/config` (`defineConfig`/`globalIgnores`), uma API exclusiva do ESLint v9 — mas o projeto declara `eslint: ^8.57.0` em `package.json`, e os pacotes `typescript-eslint`, `@eslint/js`, `globals` nem estavam listados como dependências (apenas hoisted transitivamente por outros pacotes). O lint literalmente nunca rodou com sucesso neste repositório.

**Correção aplicada** (mínima, sem upgrade de major do ESLint): `eslint.config.js` reescrito para usar o helper `tseslint.config()` (compatível com ESLint 8.57 em modo flat, sem depender de `eslint/config`), com `eslint-plugin-react-hooks` atualizado para v5.2.0 (chave correta `configs['recommended-latest']` para o formato flat — a chave `configs.recommended` da v5 é o formato legado, nome invertido do que se esperaria) e as dependências que faltavam (`typescript-eslint`, `@eslint/js`, `globals`) adicionadas a `package.json`. `@typescript-eslint/eslint-plugin`/`@typescript-eslint/parser` (não mais referenciados por ninguém no projeto) foram removidos em favor do pacote unificado `typescript-eslint`.

**Achado adicional durante o diagnóstico:** `eslint .` também tentava lintar `SobControle/` (uma cópia aninhada duplicada do próprio projeto, com seu próprio `.git`, já marcada como `# Duplicated nested project copy` no `.gitignore` — pré-existente, não criada nesta sessão, não removida por não ser escopo desta story) e `.aiox-core/` (framework AIOX, que nunca deveria ser lintado pela aplicação). Ambos adicionados a `ignores` em `eslint.config.js`.

**Resultado:** com o toolchain corrigido, `npm run lint` roda de ponta a ponta e aponta ~195 erros pré-existentes (principalmente `@typescript-eslint/no-explicit-any`, variáveis não usadas, blocos `catch` vazios) espalhados por ~40 arquivos das Stories 1.1–1.5, nenhum deles tocado por esta story. Por decisão do usuário, esses erros ficam documentados como débito técnico para uma story de limpeza dedicada — não foram corrigidos aqui para não expandir o escopo desta feature para o restante da aplicação. Todos os arquivos criados/modificados por esta story (listados em File List) passam em `npm run lint` com zero erros.
