## Story

**As an** administrador ou gerente do SobControle,
**I want** uma central que transforme estoque, vendas e compras reais em
recomendações claras de reposição, priorização e produtos parados,
**so that** eu saiba o que comprar, quanto, com que urgência e com qual
fornecedor, sem depender de estimativas inventadas e sem que o sistema tome
nenhuma ação automática por mim.

## Acceptance Criteria

1. Nova rota `/inventory/recommendations` ("Recomendações de Estoque"),
   acessível a partir de um botão no cabeçalho de Estoque (`InventoryPage`).
   Nenhuma tela, hook ou service do módulo de Estoque/Compras/Fornecedores é
   reescrito; apenas uma adição pontual (botão de navegação).
2. Recomendações de **reposição** combinam risco de ruptura + quantidade
   sugerida para o mesmo produto (evita duas listas quase idênticas): estoque
   atual, consumo médio diário (vendas válidas, exclui `payment_status =
   'cancelled'`), cobertura em dias, data estimada de ruptura quando
   calculável, quantidade em trânsito (sempre "indisponível" — o sistema
   credita estoque no ato da compra, não existe status de recebimento
   separado), quantidade sugerida, cobertura após a compra sugerida e
   justificativa textual.
3. Quantidade sugerida nunca é negativa. Fórmula: `estoque desejado =
   max(estoque mínimo, consumo médio × cobertura alvo)`; `quantidade sugerida
   = max(0, estoque desejado − estoque atual)`. Sem consumo observado, usa
   somente a regra de estoque mínimo (`max(0, estoque mínimo − estoque
   atual)`) com confiança "Baixa".
4. Recomendações de **estoque parado/excessivo** identificam produtos ativos
   sem saída válida no período configurável, exibindo quantidade disponível,
   dias sem movimentação (mínimo do período, nunca uma data inventada),
   última saída quando existir, valor estimado parado somente com custo de
   aquisição confiável (nunca `sale_price`), e ação sugerida em texto (revisar
   compra, criar promoção, reduzir reposição, revisar cadastro) — nenhum
   desconto ou preço é alterado pelo sistema.
5. Toda recomendação exibe prioridade (Crítica/Alta/Média/Baixa/Sem ação) com
   texto, ícone e descrição — nunca só cor — e nível de confiança
   (Alta/Média/Baixa) conforme a robustez do dado que a sustenta.
6. Sugestão de fornecedor é carregada sob demanda (ao abrir o detalhe), a
   partir do histórico real de `purchase_items`/`purchases` para aquele
   produto (fornecedor + custo da compra mais recente). Sem histórico de
   compra do produto, exibe literalmente "Não há dados suficientes para
   recomendar um fornecedor." Nenhuma comparação de preço é inventada.
7. Cabeçalho com filtros por categoria, fornecedor (via histórico de compra),
   prioridade, tipo de recomendação e produto; período de análise de consumo
   e cobertura alvo são ajustáveis (parâmetros de cálculo, não dados
   inventados) e indicador de última atualização.
8. Resumo executivo com cards: produtos em risco de ruptura, recomendações
   críticas, produtos parados, cobertura média de estoque (quando calculável)
   e valor estimado para reposição somente com custo confiável.
9. Cada recomendação permite: Ver produto, Ver histórico (detalhe), Dispensar,
   Adiar por 7 dias, Marcar como resolvida e, apenas para admin/manager,
   "Criar rascunho de compra" — que abre o `PurchaseModal` já existente
   pré-preenchido (produto, quantidade sugerida, fornecedor quando houver
   base), sem nunca submeter a compra automaticamente.
10. Dispensar/adiar/resolver persistem estado (`stock_recommendation_states`)
    e histórico append-only (`stock_recommendation_actions`) com usuário,
    data e motivo opcional. Nenhum registro anterior é apagado.
11. Estados de loading (skeleton), vazio, dados insuficientes, erro e acesso
    negado implementados; tooltips explicam cobertura, consumo médio, estoque
    mínimo e quantidade recomendada.
12. Isolamento por `company_id` e RLS em ambas as tabelas novas; nenhuma
    empresa acessa produtos, fornecedores, compras ou recomendações de outra.
13. Lint, typecheck, testes (cobertura, ruptura, quantidade recomendada,
    estoque excessivo, estoque mínimo, compras pendentes/indisponíveis,
    prioridade, dados insuficientes, ações de dispensar/adiar/resolver,
    isolamento por empresa) e build executados com sucesso.

## Dev Notes

### Coordenação com a branch `codex/stock-turnover-analysis`

Existe trabalho em andamento (não commitado) nesse branch/worktree, criando
uma seção de **Giro de Estoque** dentro de Relatórios (`InventoryTab.tsx`,
`reportService.ts`) — feature de **análise/relatório histórico**, distinta
desta (uma central de **recomendações acionáveis**). Nenhum arquivo daquele
branch foi tocado. As fórmulas de demanda média/cobertura/exclusão de
cancelamentos foram propositalmente mantidas idênticas às que aquele trabalho
já validou, para não haver dois números diferentes para o mesmo conceito
quando os branches forem integrados. Quando `codex/stock-turnover-analysis`
for mesclado, há uma oportunidade de extrair um util compartilhado
(`inventoryConsumption.ts`) usado por ambas as features — não feito agora
para não depender de código que não existe nesta branch.

### Dados confirmados (mesma conclusão do branch de giro de estoque + verificação própria)

- `products`: estoque atual, estoque mínimo, custo, categoria, SKU, código de
  barras, ativo — real, sempre com `company_id`.
- `sale_items` + `sales`: saída válida = `payment_status <> 'cancelled'`
  (grafia exata usada em `salesService.ts`).
- `purchase_items` + `purchases`: usados apenas para sugestão de fornecedor
  (último fornecedor/custo por produto), nunca como "consumo".
- **Não existe** estoque em trânsito/pendente de recebimento: `createPurchase`
  credita `products.current_quantity` no ato, independente do status de
  pagamento — não há um segundo estado "recebido". Todo campo relacionado é
  exibido como indisponível, nunca como zero silencioso.
- **Não existe** lead time/prazo de entrega em `suppliers` nem em `products`.
- **Não existe** estoque reservado (Pipeline não referencia produtos; vendas
  são imediatas).
- **Não existe** ledger/snapshot histórico de estoque — giro clássico
  permanece indisponível (mesma conclusão da story de Giro de Estoque).

### Deliberadamente não implementado

- Prazo médio de entrega por fornecedor — dado inexistente.
- Quantidade em trânsito real — dado inexistente (sempre "indisponível").
- Comparação de preços entre fornecedores — só há histórico do último
  fornecedor usado por produto, não uma cesta comparável.
- Reconstrução de estoque médio histórico para giro clássico.

### Parâmetros de cálculo (não são dados armazenados, são ajustáveis pelo usuário na tela)

- Período de análise de consumo: 7/30/60/90 dias, padrão 30.
- Cobertura alvo: 7/14/30 dias, padrão 14 — usado apenas para calcular
  "estoque desejado"; não existe essa configuração por empresa hoje.

### Fora de escopo (não tocado)

- `src/pages/reports/**`, `src/services/reportService.ts` — pertence à story
  de Giro de Estoque em andamento em outro worktree.
- Pipeline, Agenda, Financeiro, Notificações — não alterados.
- Nenhuma compra ou ajuste de estoque é criado automaticamente; toda ação
  exige confirmação explícita do usuário no `PurchaseModal` já existente.
