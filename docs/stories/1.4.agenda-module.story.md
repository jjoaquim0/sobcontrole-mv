## Story

**As a** vendedor, gerente ou administrador logado no SobControle,
**I want** uma Agenda/Calendário em `/agenda`, com visões de mês, semana e dia, onde eu possa criar, editar e excluir compromissos (reunião, tarefa, ligação, visita, lembrete), associá-los a clientes e negócios do pipeline, e filtrar por responsável/tipo/status/cliente,
**so that** eu possa organizar minha rotina comercial e operacional dentro do CRM, sem depender de agendas externas, mantendo o isolamento de dados da minha empresa (multitenancy).

**Task 1 — Schema do banco (`appointments`):**

7. Nenhuma tabela `appointments`/`events`/`tasks`/`activities`/`meetings`/`reminders`/`interactions` pré-existia no schema (confirmado via `mcp__supabase__list_tables` antes da implementação) — uma tabela nova foi criada, seguindo o padrão de multitenancy do projeto (`company_id UUID REFERENCES companies(id) ON DELETE CASCADE NOT NULL`, RLS `FOR ALL USING (company_id = get_user_company_id())`, `REVOKE ALL ... FROM anon`):

```sql
CREATE TABLE IF NOT EXISTS appointments (
    id UUID PRIMARY KEY,
    company_id UUID REFERENCES companies(id) ON DELETE CASCADE NOT NULL,
    customer_id UUID REFERENCES customers(id) ON DELETE SET NULL,
    deal_id UUID REFERENCES deals(id) ON DELETE SET NULL,
    assigned_user_id UUID REFERENCES profiles(id) ON DELETE RESTRICT NOT NULL,
    created_by UUID REFERENCES profiles(id) ON DELETE SET NULL,
    title TEXT NOT NULL,
    description TEXT DEFAULT '',
    type TEXT NOT NULL DEFAULT 'reuniao',
    status TEXT NOT NULL DEFAULT 'agendado',
    start_at TIMESTAMPTZ NOT NULL,
    end_at TIMESTAMPTZ NOT NULL,
    all_day BOOLEAN NOT NULL DEFAULT false,
    location TEXT DEFAULT '',
    notes TEXT DEFAULT '',
    created_at TIMESTAMPTZ DEFAULT now() NOT NULL,
    updated_at TIMESTAMPTZ DEFAULT now() NOT NULL,
    CONSTRAINT appointments_end_after_start CHECK (end_at >= start_at),
    CONSTRAINT appointments_type_check CHECK (type IN ('reuniao', 'tarefa', 'ligacao', 'visita', 'lembrete')),
    CONSTRAINT appointments_status_check CHECK (status IN ('agendado', 'confirmado', 'concluido', 'cancelado', 'nao_compareceu', 'pendente'))
);

CREATE INDEX IF NOT EXISTS idx_appointments_company_start ON appointments(company_id, start_at);
CREATE INDEX IF NOT EXISTS idx_appointments_assigned_user ON appointments(assigned_user_id);
CREATE INDEX IF NOT EXISTS idx_appointments_customer ON appointments(customer_id);
CREATE INDEX IF NOT EXISTS idx_appointments_deal ON appointments(deal_id);

ALTER TABLE appointments ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Acesso total dos membros da empresa aos compromissos" ON appointments
FOR ALL USING (company_id = get_user_company_id());

REVOKE ALL ON appointments FROM anon;
```

8. **Suposição assumida e documentada:** `customer_id`/`deal_id` são opcionais (`ON DELETE SET NULL`) porque um compromisso pode ser puramente operacional (ex.: lembrete interno, tarefa administrativa) sem cliente ou negócio relacionado — o brief pedia "cliente relacionado, se aplicável" e "associar a oportunidade/negócio, se houver base pronta". `assigned_user_id` (responsável) é obrigatório (`ON DELETE RESTRICT`), pois todo compromisso deve aparecer na agenda de alguém.
9. **Suposição assumida e documentada:** validação de coerência de datas (`end_at >= start_at`) feita via `CHECK` constraint no banco — camada de defesa adicional além da validação Zod no formulário, evitando dados inconsistentes por chamadas diretas à API.
10. Nenhum seed de dados foi necessário (diferente da Story 1.3/`pipeline_stages`): os 5 tipos e 6 status de compromisso são enums fixos validados por `CHECK`, não linhas configuráveis por empresa — não há "etapas" a semear.
11. Migration aplicada com sucesso ao projeto Supabase remoto via MCP (`mcp__supabase__apply_migration`) durante esta story — não ficou pendente de aplicação manual. Verificado por `mcp__supabase__get_advisors(type: security)` que nenhum novo aviso de RLS foi introduzido pela tabela `appointments` (os avisos remanescentes são pré-existentes — funções `SECURITY DEFINER` e proteção de senha vazada — e não relacionados a esta story).
12. Migration espelhada em `supabase/migrations/20260705010000_agenda_module_schema.sql` e em `supabase_schema.sql` (tabela, índices, RLS, REVOKE), conforme convenção do projeto.

### Data/hora sem biblioteca externa

Nenhuma biblioteca de data (`date-fns`, `dayjs`, `luxon`) existe no projeto (confirmado por busca em `package.json`). Todos os helpers de calendário em `src/pages/agenda/utils.ts` usam `Date` nativo. A conversão entre os campos de formulário (`<input type="date">`/`<input type="time">`, sempre em horário local do navegador) e o armazenamento (`TIMESTAMPTZ`, gravado como ISO/UTC) segue o padrão: construir um `Date` local a partir dos componentes (`new Date(y, m-1, d, hh, mi)`) e só chamar `.toISOString()` na fronteira de gravação (`combineDateTime`); na leitura, usar os getters locais (`getFullYear`/`getMonth`/`getDate`/`getHours`/`getMinutes`) para popular os inputs — nunca `toISOString().slice(...)`, que retornaria componentes em UTC e deslocaria a hora exibida em fusos não-UTC. Essa é a mesma categoria de cuidado que gerou o bug de fuso corrigido na v0.2 da Story 1.3 (`isDealOverdue`), mas resolvida aqui construindo os `Date` sempre a partir de componentes locais explícitos, em vez de comparar strings de data isoladas. [Source: src/services/dealsService.ts:7-11 — `isDealOverdue`, Change Log da Story 1.3 v0.2]

### Visão de Semana — decisão de escopo (não é uma grade horária pixel-precisa)

**Suposição assumida e documentada:** a visão "Semana" (`CalendarWeekView.tsx`) exibe 7 colunas (uma por dia), cada uma listando os compromissos daquele dia em ordem cronológica ("agenda" por dia), e não uma grade horária com uma linha por hora e posicionamento vertical proporcional ao horário (estilo Google Calendar). Implementar uma grade horária pixel-precisa exigiria cálculo de sobreposição de eventos simultâneos, scroll sincronizado entre colunas e uma unidade de medida (pixels por minuto) sem nenhum precedente no design system atual — esforço desproporcional ao MVP pedido, que exige apenas "visão semanal" sem especificar granularidade horária visual. A visão de Dia (`CalendarDayView.tsx`) compensa isso parcialmente ao exibir claramente o horário de início/término de cada compromisso em texto. Uma story futura pode evoluir a Semana para uma grade horária caso o time sinta falta dessa granularidade.

### Drag and drop — limitado à visão de Mês

**Suposição assumida e documentada:** o escopo desejável do brief pedia "drag and drop para mudar horário/data de compromissos". Implementado apenas na visão de Mês (arrastar entre dias, preservando o horário original) — reaproveita `@dnd-kit/core` (já instalado na Story 1.3) sem exigir nova dependência. Drag-and-drop para mudar apenas o *horário* dentro do mesmo dia (arrastar verticalmente numa grade horária) não foi implementado, pois depende da grade horária pixel-precisa não construída nesta story (ver decisão acima sobre a visão de Semana). Reagendar o horário de um compromisso hoje é feito editando o modal.

### Criação por clique — granularidade diária, não por horário

**Suposição assumida e documentada:** clicar numa célula de dia vazio (Mês/Semana) abre o modal de criação pré-preenchido com a data clicada e horário padrão `09:00–10:00` (ajustável no formulário). Como nenhuma das visões usa uma grade horária clicável célula-a-célula, não é possível pré-selecionar o horário exato a partir do clique — apenas a data.
