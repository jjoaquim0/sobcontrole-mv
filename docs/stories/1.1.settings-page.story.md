## Story

**As a** administrador ou gerente da empresa (admin/manager) logado no SobControle,
**I want** uma página de Configurações Gerais em `/settings`, integrada ao layout existente da aplicação, com abas para dados da empresa, aparência, notificações, segurança, integrações, equipe, assinatura e dados,
**so that** eu possa gerenciar as configurações operacionais e de conta da minha empresa sem precisar de suporte técnico, mantendo controle total sobre time, aparência, segurança e dados exportáveis.

## Acceptance Criteria

**Geral / Estrutura (Tasks 5 e 6):**

1. A rota `/settings` já existe em `src/routes/index.tsx`, protegida por `RoleRoute allowedRoles={['admin', 'manager']}` dentro de `AppLayout` — o componente `Settings` (atualmente placeholder `UnderConstruction`) deve ser substituído pela implementação completa, sem alterar a rota ou as permissões de acesso.
2. A página NÃO recria fundo, navbar, sidebar ou vídeo — ela renderiza apenas o conteúdo interno, pois já é filha de `AppLayout` (que já provê sidebar + header). Nenhuma duplicação de chrome de layout é permitida.
3. Background da página usa `bg-[#f0f2f5] dark:bg-[#0f1117]`; todos os cards usam `bg-white dark:bg-[#1a1d27] border border-gray-100 dark:border-white/5 rounded-2xl`.
4. Estrutura de arquivos criada: `src/pages/settings/SettingsPage.tsx`, `src/pages/settings/SettingsSidebar.tsx`, `src/pages/settings/index.tsx` (substitui o placeholder atual), e `src/pages/settings/tabs/{GeneralTab,AppearanceTab,NotificationsTab,SecurityTab,IntegrationsTab,TeamTab,SubscriptionTab,DataTab}.tsx`.
5. `SettingsSidebar` navega entre as 8 abas via estado local (tab ativa), sem criar sub-rotas novas (a rota continua sendo apenas `/settings`).
6. Zero comentários no código; todo texto visível ao usuário em PT-BR; TypeScript estrito (sem `any` não justificado); ícones via `lucide-react`; formulários com React Hook Form + Zod; feedback de sucesso/erro via `sonner` (`toast`); estados de carregamento usam `Loader2` (lucide) com `animate-spin`.

**Task 1 — Schema do banco (`company_settings`):**

7. Migration SQL criada em `supabase/migrations/` contendo exatamente o DDL abaixo (sem alterações), incluindo `ENABLE ROW LEVEL SECURITY`, a policy `"Acesso total dos membros da empresa às configurações"` usando `get_user_company_id()`, e o `REVOKE ALL ... FROM anon`:

```sql
CREATE TABLE IF NOT EXISTS company_settings (
    id UUID PRIMARY KEY,
    company_id UUID REFERENCES companies(id) ON DELETE CASCADE UNIQUE NOT NULL,
    timezone TEXT DEFAULT 'America/Sao_Paulo',
    currency TEXT DEFAULT 'BRL',
    language TEXT DEFAULT 'pt-BR',
    date_format TEXT DEFAULT 'DD/MM/YYYY',
    logo_url TEXT DEFAULT '',
    primary_color TEXT DEFAULT '#10b981',
    email_notifications BOOLEAN DEFAULT true,
    push_notifications BOOLEAN DEFAULT true,
    whatsapp_notifications BOOLEAN DEFAULT false,
    created_at TIMESTAMPTZ DEFAULT now() NOT NULL,
    updated_at TIMESTAMPTZ DEFAULT now() NOT NULL
);
ALTER TABLE company_settings ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Acesso total dos membros da empresa às configurações" ON company_settings
FOR ALL USING (company_id = get_user_company_id());
REVOKE ALL ON company_settings FROM anon;
```

8. Antes de escrever a migration, `@dev`/`@data-engineer` deve confirmar que a função `get_user_company_id()` já existe no schema do projeto (buscar em migrations existentes ou no schema atual); se não existir ainda no ambiente-alvo, documentar isso explicitamente em Dev Notes/Debug Log — **não inventar** a definição da função, apenas relatar o gap.
9. `company_id` é `UNIQUE` — ou seja, cada empresa tem exatamente uma linha de settings (upsert pattern no service, não múltiplas linhas).

**Task 2 — Types (`src/types/index.ts`):**

10. Interface `CompanySettings` adicionada em `src/types/index.ts`, seguindo o padrão camelCase já usado nas demais interfaces do arquivo (ex.: `Supplier`, `Customer`), mapeando 1:1 os campos da tabela `company_settings` (id, companyId, timezone, currency, language, dateFormat, logoUrl, primaryColor, emailNotifications, pushNotifications, whatsappNotifications, createdAt, updatedAt).

**Task 3 — Service (`src/services/settingsService.ts`):**

11. Arquivo criado com as funções: `getSettings`, `updateSettings`, `updateCompanyLogo`, `changePassword`, `getTeamMembers`, `inviteTeamMember`, `removeTeamMember`, `updateMemberRole`, `exportAllData`, `getApiKeys`, `createApiKey`, `revokeApiKey`.
12. Todas as funções que leem/escrevem `company_settings`, `profiles` (membros do time) ou dados relacionados à empresa devem filtrar por `company_id` obtido de `useAuthStore.getState().company?.id`, seguindo exatamente o padrão de `src/services/supplierService.ts` (mapper snake_case→camelCase, checagem de `companyId` ausente lançando `Error('Empresa não identificada.')`).
13. `changePassword` usa `supabase.auth.updateUser({ password })`.
14. `updateCompanyLogo` faz upload para o Supabase Storage e retorna a `logo_url` pública, persistindo-a via `updateSettings`.
15. `getApiKeys`/`createApiKey`/`revokeApiKey`: como não existe tabela de API keys especificada no schema fornecido acima, e Article IV proíbe invenção de schema não solicitado, o `@dev` deve tratar este conjunto de funções como **funcionalidade de UI com persistência mockada/local (placeholder)** até que uma tabela dedicada seja especificada em story futura — isso deve ser documentado claramente em Dev Notes e no código (nome de função real, mas sem tabela SQL inventada). Esse tratamento é uma decisão de escopo, registrada como AUTO-DECISION abaixo.
16. `getTeamMembers`/`inviteTeamMember`/`removeTeamMember`/`updateMemberRole` operam sobre a tabela `profiles` já existente (via `company_id`), reaproveitando o tipo `Profile` de `src/types/index.ts`. `inviteTeamMember` não deve inventar fluxo de e-mail transacional — deve documentar como placeholder caso não haja Edge Function de convite especificada.

**Task 4 — Hook (`src/hooks/useSettings.ts`):**

17. Hook criado seguindo o padrão de `src/hooks/useSuppliers.ts`: `useQuery` para `settings` (`queryKey: ['settings']`), `team` (`queryKey: ['team']`) e `apiKeys` (`queryKey: ['apiKeys']`); `useMutation` para cada ação de escrita (`updateSettings`, `updateCompanyLogo`, `changePassword`, `inviteTeamMember`, `removeTeamMember`, `updateMemberRole`, `createApiKey`, `revokeApiKey`, `exportAllData`), cada mutation invalidando a query relacionada em `onSuccess` e disparando `toast.error` com a mensagem de erro em `onError`.

**Task 7 — Abas (uma AC por aba):**

18. **GeneralTab**: formulário RHF+Zod com nome da empresa (editável, atualiza `companies.name`), CNPJ (campo readonly), timezone, moeda, idioma e formato de data (todos editáveis, persistidos em `company_settings` via `updateSettings`); botão "Salvar" com estado de loading (`Loader2`) e `toast.success`/`toast.error`.
19. **AppearanceTab**: toggle de tema conectado a `useThemeStore` (`toggleTheme`/`theme`); upload de logo com preview local (antes do upload) e preview persistido (após), usando Supabase Storage; seletor de cor primária com `<input type="color">` e presets fixos `#10b981`, `#3b82f6`, `#8b5cf6`, `#f59e0b`.
20. **NotificationsTab**: 3 toggles (email, push, whatsapp); toggle "whatsapp" renderizado desabilitado com indicação visual de "em breve"/placeholder (não persiste alteração real).
21. **SecurityTab**: formulário de troca de senha (RHF+Zod, `supabase.auth.updateUser`) com validação de confirmação de senha; seção "Autenticação em Duas Etapas (2FA)" com texto "Em breve"; seção "Sessões Ativas" como placeholder informativo (sem dados reais, já que não há tabela de sessões especificada).
22. **IntegrationsTab**: lista de API keys (mock/local, ver AC 15) com ação "Revogar" por linha; modal de criação de nova chave que exibe o valor da chave **uma única vez** com botão de copiar para a área de transferência (`navigator.clipboard.writeText`).
23. **TeamTab**: `DataTable` (reaproveitando `src/components/shared/DataTable.tsx`) listando membros com avatar (iniciais ou imagem), nome, e-mail, seletor de papel (role), status e ações; modal "Convidar Membro"; `ConfirmModal` (reaproveitando `src/components/shared/ConfirmModal.tsx`, variant `danger`) para remoção; a ação de remover NÃO pode ser exibida/permitida para o próprio usuário logado (`profile.id === member.id` deve ocultar/desabilitar o botão de remover).
24. **SubscriptionTab**: exibe plano atual e uso a partir de `useAuth()` (`subscription`, `company`); botão "Gerenciar Assinatura" como placeholder (sem integração de billing real); seção de histórico de faturas como placeholder informativo.
25. **DataTab**: botão "Exportar Tudo" gera download de um arquivo `.json` no client (via `Blob` + link temporário) com os dados retornados por `exportAllData`; seção "Importar Dados" com texto "Em breve"; botão "Limpar Dados de Teste" com `ConfirmModal` variant `danger`, texto explícito de perigo/irreversibilidade.
