## Story

**As a** administrador ou gerente da empresa (admin/manager) logado no SobControle,
**I want** um módulo Financeiro completo em `/financial`, integrado às contas a receber geradas pelas vendas e às contas a pagar geradas pelas compras, com suporte a lançamentos manuais, categorização e fluxo de caixa,
**so that** eu possa controlar entradas e saídas financeiras da minha empresa, marcar contas como pagas/recebidas, e visualizar minha posição de caixa sem depender de planilhas externas.

**Task 1 — Schema do banco (ALTER TABLE + nova tabela `financial_categories`):**

7. Migration SQL criada em `supabase/migrations/` (e refletida em `supabase_schema.sql` conforme convenção do projeto) contendo exatamente o DDL abaixo, sem alterações de nomes de coluna, tipos ou defaults:

```sql
ALTER TABLE account_receivables
  ADD COLUMN IF NOT EXISTS payment_method TEXT DEFAULT '',
  ADD COLUMN IF NOT EXISTS paid_at TIMESTAMPTZ;

ALTER TABLE account_payables
  ADD COLUMN IF NOT EXISTS purchase_id TEXT REFERENCES purchases(id) ON DELETE SET NULL,
  ADD COLUMN IF NOT EXISTS supplier_id UUID REFERENCES suppliers(id) ON DELETE RESTRICT,
  ADD COLUMN IF NOT EXISTS payment_method TEXT DEFAULT '',
  ADD COLUMN IF NOT EXISTS paid_at TIMESTAMPTZ;

CREATE TABLE IF NOT EXISTS financial_categories (
    id UUID PRIMARY KEY,
    company_id UUID REFERENCES companies(id) ON DELETE CASCADE NOT NULL,
    name TEXT NOT NULL,
    type TEXT NOT NULL DEFAULT 'expense', -- 'revenue', 'expense'
    color TEXT DEFAULT '#10b981',
    created_at TIMESTAMPTZ DEFAULT now() NOT NULL,
    updated_at TIMESTAMPTZ DEFAULT now() NOT NULL
);
ALTER TABLE financial_categories ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Acesso total dos membros da empresa às categorias financeiras" ON financial_categories
FOR ALL USING (company_id = get_user_company_id());
REVOKE ALL ON financial_categories FROM anon;
```

8. `account_payables.supplier_id` é adicionada como `REFERENCES suppliers(id) ON DELETE RESTRICT` sem `NOT NULL` (a tabela já possui linhas legadas sem esse valor preenchido, criadas por `purchaseService.createPurchase()` antes desta story); novas linhas inseridas a partir desta story DEVEM preencher `supplier_id` e `purchase_id`. Não tornar a coluna `NOT NULL` nesta migration para não quebrar dados existentes.
9. `account_payables.purchase_id` corrige uma referência já usada implicitamente pelo código: `src/services/purchaseService.ts` já executa `.eq('purchase_id', id)` em updates de `account_payables` (linhas ~279-282 e ~323-326) mesmo a coluna não existindo hoje no schema — essa migration corrige esse gap latente. `@dev` deve confirmar, após aplicar a migration, que esses updates existentes continuam funcionando corretamente (idealmente também populando `purchase_id` no INSERT de `purchaseService.createPurchase()`, ajustado na Task 3 desta story).
10. `financial_categories.type` segue o mesmo padrão de enum-as-TEXT usado em `status` de outras tabelas do schema (comentário inline com os valores permitidos, sem `CHECK` constraint, consistente com `account_receivables.status`/`account_payables.status`).
