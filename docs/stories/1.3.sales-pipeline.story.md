## Story

**As a** vendedor, gerente ou administrador logado no SobControle,
**I want** um Kanban de Pipeline de Vendas em `/pipeline`, com etapas do funil configuráveis por empresa, cards de oportunidades que posso arrastar entre etapas, criar, editar, filtrar e encerrar (Ganho/Perdido),
**so that** eu possa visualizar e conduzir minhas negociações comerciais de forma visual, sem depender de planilhas externas, mantendo o isolamento de dados da minha empresa (multitenancy).

**Task 1 — Schema do banco (`pipeline_stages`, `deals`, `deal_stage_history`):**

7. Nenhuma tabela `deals`/`opportunities`/`pipelines`/`stages` pré-existia no schema (confirmado via leitura de `supabase_schema.sql` e `mcp__supabase__list_tables` antes da implementação) — três tabelas novas foram criadas, seguindo exatamente o padrão de multitenancy do projeto (`company_id UUID REFERENCES companies(id) ON DELETE CASCADE NOT NULL`, RLS `FOR ALL USING (company_id = get_user_company_id())`, `REVOKE ALL ... FROM anon`):

```sql
CREATE TABLE IF NOT EXISTS pipeline_stages (
    id UUID PRIMARY KEY,
    company_id UUID REFERENCES companies(id) ON DELETE CASCADE NOT NULL,
    name TEXT NOT NULL,
    color TEXT NOT NULL DEFAULT '#10b981',
    position DOUBLE PRECISION NOT NULL DEFAULT 0,
    is_active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ DEFAULT now() NOT NULL,
    updated_at TIMESTAMPTZ DEFAULT now() NOT NULL
);

CREATE TABLE IF NOT EXISTS deals (
    id UUID PRIMARY KEY,
    company_id UUID REFERENCES companies(id) ON DELETE CASCADE NOT NULL,
    title TEXT NOT NULL,
    customer_id UUID REFERENCES customers(id) ON DELETE RESTRICT NOT NULL,
    owner_id UUID REFERENCES profiles(id) ON DELETE RESTRICT NOT NULL,
    stage_id UUID REFERENCES pipeline_stages(id) ON DELETE RESTRICT NOT NULL,
    value NUMERIC(12, 2) DEFAULT 0.00 NOT NULL,
    status TEXT NOT NULL DEFAULT 'open', -- 'open', 'won', 'lost'
    expected_close_date DATE,
    position DOUBLE PRECISION NOT NULL DEFAULT 0,
    notes TEXT DEFAULT '',
    lost_reason TEXT,
    closed_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ DEFAULT now() NOT NULL,
    updated_at TIMESTAMPTZ DEFAULT now() NOT NULL
);

CREATE TABLE IF NOT EXISTS deal_stage_history (
    id UUID PRIMARY KEY,
    deal_id UUID REFERENCES deals(id) ON DELETE CASCADE NOT NULL,
    from_stage_id UUID REFERENCES pipeline_stages(id) ON DELETE SET NULL,
    to_stage_id UUID REFERENCES pipeline_stages(id) ON DELETE RESTRICT NOT NULL,
    changed_by UUID REFERENCES profiles(id) ON DELETE SET NULL,
    changed_at TIMESTAMPTZ DEFAULT now() NOT NULL
);

ALTER TABLE pipeline_stages ENABLE ROW LEVEL SECURITY;
ALTER TABLE deals ENABLE ROW LEVEL SECURITY;
ALTER TABLE deal_stage_history ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Acesso total dos membros da empresa às etapas do pipeline" ON pipeline_stages
FOR ALL USING (company_id = get_user_company_id());

CREATE POLICY "Acesso total dos membros da empresa aos negócios" ON deals
FOR ALL USING (company_id = get_user_company_id());

CREATE POLICY "Acesso total ao histórico de negócios da empresa" ON deal_stage_history
FOR ALL USING (
  EXISTS (SELECT 1 FROM public.deals WHERE deals.id = deal_stage_history.deal_id AND deals.company_id = get_user_company_id())
);

REVOKE ALL ON pipeline_stages, deals, deal_stage_history FROM anon;
```

8. **Suposição assumida e documentada:** `position` em `pipeline_stages`/`deals` é `DOUBLE PRECISION` (não `INTEGER`), permitindo reordenação manual por inserção de ponto médio (ex.: mover um card entre posições 1 e 2 grava 1.5) sem precisar renumerar as demais linhas da coluna a cada drag and drop — decisão de implementação, não uma tabela/coluna inventada além do escopo pedido.
9. **Suposição assumida e documentada:** `deals.status` (`'open'|'won'|'lost'`) é um campo independente de `stage_id`. O Kanban exibe por padrão apenas negócios `status = 'open'`; a ação "Marcar como Ganho/Perdido" fecha o negócio (grava `closed_at`) e o remove do board, preservando o histórico no banco. Essa decisão foi necessária para que a métrica "valor total em pipeline" pedida no brief tenha significado correto (soma apenas do que está genuinamente em aberto), evitando que negócios já encerrados inflem o total indefinidamente.
10. Seed de 5 etapas padrão (`Novo Contato`, `Qualificação`, `Proposta Enviada`, `Negociação`, `Fechamento`, cores fixas) inserido para todas as empresas já existentes na migration, e `complete_company_signup()` (função já existente, usada no cadastro de novas empresas) foi atualizada (`CREATE OR REPLACE`, mesma assinatura/retorno) para semear as mesmas 5 etapas em toda empresa criada a partir de agora — sem isso, empresas novas nasceriam com um board vazio e sem etapas utilizáveis.
11. Migration aplicada com sucesso ao projeto Supabase remoto via MCP (`mcp__supabase__apply_migration`) durante esta story — não ficou pendente de aplicação manual. Verificado por query direta (`SELECT ... FROM pipeline_stages`) que as duas empresas existentes já possuem as 5 etapas seedadas, e por `mcp__supabase__get_advisors(type: security)` que nenhum novo aviso de RLS foi introduzido pelas 3 tabelas novas (avisos remanescentes são pré-existentes e não relacionados a esta story).
12. Migration espelhada em `supabase/migrations/20260705000000_sales_pipeline_module_schema.sql` e em `supabase_schema.sql` (tabelas, RLS, REVOKE, e a função `complete_company_signup` atualizada), conforme convenção do projeto.

**Task 3 — Service (`src/services/dealsService.ts`):**

17. Funções criadas: `getPipelineStages()`, `getDeals(filters?)`, `createDeal(data)`, `updateDeal(id, data)`, `moveDealStage(id, toStageId, position)`, `closeDeal(id, status, lostReason?)`, `getDealHistory(dealId)`, seguindo exatamente o padrão de `src/services/salesService.ts` (mapper `mapDbX` snake_case→camelCase, `companyId` via `useAuthStore.getState().company?.id`, erro `throw new Error('Empresa não identificada.')` quando ausente, filtro `.eq('company_id', companyId)` em toda query, `id: crypto.randomUUID()` para as tabelas com PK UUID — mesmo padrão de `customerService.ts`/`supplierService.ts`/`documentService.ts`).
18. `getDeals(filters)` filtra por padrão `status = 'open'` (o board não exibe negócios encerrados), com filtros opcionais de `ownerId`, `stageId` e busca textual (client-side, por título do negócio ou nome do cliente, mesmo padrão de `getSales`).
19. `createDeal`/`moveDealStage` gravam uma linha em `deal_stage_history` a cada mudança de etapa (na criação, `from_stage_id = null`; na movimentação, `from_stage_id` é obtido por um `SELECT` do valor atual antes do `UPDATE`), implementando o histórico básico de movimentação pedido no escopo desejável.
20. `closeDeal(id, status, lostReason?)` grava `status`, `closed_at = now()` e `lost_reason` (apenas quando `status = 'lost'`).

**Task 4 — Hook (`src/hooks/usePipeline.ts`):**

21. `usePipelineStages()`, `useDeals(filters)`, `useDealHistory(dealId)` via `useQuery` (`queryKey`: `['pipeline-stages']`, `['deals', filters]`, `['deal-history', dealId]`).
22. `useDealMutations(filters)` com `useMutation` para `createDeal`, `updateDeal`, `moveDeal`, `closeDeal`; todas invalidam `['deals']` e `['dashboard']` em `onSuccess`/`onSettled`, e disparam `toast.error`/`toast.success`, seguindo o padrão de `useSaleMutations`.
23. `moveDeal` implementa atualização otimista (escopo desejável): `onMutate` atualiza a cache local de `['deals', filters]` imediatamente (sem esperar round-trip do servidor), `onError` reverte para o snapshot anterior via `context.previous` e exibe `toast.error`, `onSettled` invalida `['deals']` para reconciliar com o servidor.

### Drag and drop — decisão de dependência nova

Nenhuma biblioteca de drag-and-drop (`@dnd-kit/*`, `react-beautiful-dnd`, `react-dnd`) existia no projeto antes desta story (confirmado por busca em `package.json`/`package-lock.json`). `framer-motion` (já instalado, `^11.0.8`) oferece primitivos de `drag`, mas não uma solução pronta de múltiplos containers com detecção de colisão/drop-zones — implementar isso manualmente seria um esforço desproporcional e sem precedente no código atual. `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities` foram adicionados como a escolha padrão do ecossistema React para esse caso de uso. - **Gestão de etapas do pipeline (criar/editar/reordenar etapas pela UI)**: o escopo desejável do brief condicionava essa funcionalidade a "se houver base pronta no projeto" — não havia nenhuma base (nenhuma tabela/UI de etapas pré-existente). Reversão hoje exigiria update direto no banco. Recomenda-se uma story futura de "Histórico de Negócios" caso esse fluxo seja necessário.
